# Performance evidence

The production demo build emits `.certification/performance/topology.json` from Rollup's actual output graph. Each chunk records static/dynamic dependencies, initial reachability, raw/gzip bytes, contributing modules, rendered lengths and source importers. No chunk partitioning changed for this audit.

The first post-contract baseline contains 963,296 bytes of statically reachable initial JavaScript (171,820 gzip bytes). The composer chunk is 97,654 bytes. The largest deferred chunk is 356,527 bytes; despite its ChartPoint filename, its largest contributors are generated preview loaders, the demo application and registry metadata. The component registry's 271,760-byte chunk is initial. Module names alone do not identify bundle responsibility.

`pnpm performance:check` enforces recorded candidate regression ceilings approximately ten percent above that measured baseline. Raising a ceiling requires a documented cause and review, not blindly accepting changed output. These ceilings establish regression checks, not enterprise interaction-time or memory readiness. The bundle check does not measure route bytes, registry import latency, interaction readiness or memory; the separate runtime collector below measures its stated scope. Browser network activity may load additional deferred chunks beyond the static initial closure.

`pnpm performance:runtime` launches its own loopback preview on an allocated port and measures three fresh contexts per engine at 1440 and 390 pixels (18 browser trials). It verifies an actual dialog interaction, records resource-timing script bytes, and measures Chromium JS heap through CDP. Fifteen fresh Node processes measure five registry imports, including I/O, parsing and evaluation. Candidate ceilings are stored separately in `beta/runtime-performance-budgets.json`.

Navigation-to-verified-interaction is a directly observed readiness metric, not a standards TTI score. Firefox/WebKit heap measurements remain NOT_RUN because this collector uses Chromium CDP. Registry import latency is not isolated parser time. These scope limits accompany every runtime report, and enterprise hardware/network/latency acceptance still needs owner review.
