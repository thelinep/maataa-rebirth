# Composition grammar and provenance

Canonical IDs remain owned by existing workspace/page/layout/region/component/atomic catalogues. Generated relationship facts are derived from the eight compatibility tuples and audited LayoutPreset slots: 2,316 declared edges. They carry source/default/demo provenance, not fabricated runtime qualification. `evaluateCompositionRelationship` distinguishes identity existence from relationship status and returns unverified for absent edges. Status vocabulary includes verified, declared, recommended, unverified, denied and deprecated; no denial is inferred from missing knowledge.

Region→component and component→atom compatibility remains unverified where implementation evidence is unavailable. Application-specific relationships must supply provenance rather than be inferred from names or product domains.

The nine implemented composer block bindings are generated by matching ComposerRenderer import origins to COMPONENT_REGISTRY leaf exports. This avoids confusing the data DataTable with the identically named tool. Code generation consumes those bindings; no separate import ontology is maintained.

Regenerate with `node scripts/generate-composition-contracts.mjs`; check with `--check`. Phase E development checks: TypeScript, 190 unit tests, fresh production demo build and 42 Chromium desktop/mobile tests passed; no dynamic/static collision warnings.
